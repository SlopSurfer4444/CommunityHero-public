# Local account-bound engine adapters

`bridge.mjs` consumes one JSON request and emits one JSON envelope. Provider, material and media requests must carry an explicit `account`; the allowlist is `likeavto` and `baw-russia`. There is no adapter-side account fallback. The UI and server may keep LikeAvto as their legacy default, but they must put the selected provider key in every bridge request.

`config.mjs` derives one card and one private Provider config from that key and rejects cross-account bindings. Each request checks `stableAccountKey`, the primary object, the bounded account object list and the live authorized-object catalogue before ordinary provider reads or writes. It never returns credential references. Normal development retains the existing workstation defaults. `COMMUNITYHERO_CONVEYOR_ROOT` and `COMMUNITYHERO_CONVEYOR_REPO` are aliases, as are `COMMUNITYHERO_PROVIDER_ROOT` and `COMMUNITYHERO_PROVIDER_REPO`; any simultaneously supplied values must resolve to the same absolute path. `COMMUNITYHERO_PROVIDER_RUNTIME`, `COMMUNITYHERO_PROVIDER_CONFIG`, `COMMUNITYHERO_ACCOUNT_CARD` and `COMMUNITYHERO_PROVIDER_NODE` accept absolute overrides. An explicit function option must agree with a supplied environment binding; conflicting bindings fail instead of falling back. Config and card overrides may use arbitrary filenames, but their contents must name the requested account. An explicit Provider root is authoritative during relocation, so an older absolute `provider_root` in the card is allowed; without an explicit root, the card root must equal the selected Provider repository.

Set `COMMUNITYHERO_RUNTIME_MODE=portable` for a relocated adapter. In this mode, the conveyor and Provider roots, Provider config, account card and Provider Node must all be supplied explicitly; workstation defaults cannot fill missing bindings. Provider runtime may be supplied separately or derived from the explicit conveyor root. Missing bindings and cross-account content fail closed before Provider access. Portable assistant work separately requires absolute `COMMUNITYHERO_CODEX_CLI` and `COMMUNITYHERO_ASSISTANT_DATA_DIR`. Portable materials/media require absolute `COMMUNITYHERO_PYTHON`, `COMMUNITYHERO_MATERIALS_SOURCE_DB` and `COMMUNITYHERO_MATERIALS_DATA_DIR`; the selected account card is passed to Python and rechecked by its contents. The common card derives from the selected conveyor root. Local media databases and scratch paths remain separated by account under the configured materials directory. Normal mode retains existing defaults for these paths.

`caps` returns the local adapter contract version and account binding plus ProviderLab's offline `capabilities` result. It does not construct a credential runtime or make a network request. Local capabilities are the effective consumer surface and currently admit `close`, `delete`, `hide` and `reply_and_close`. `scan` passes the bounded ProviderLab 1.1 scan contract for resumable multi-status discovery. The older `read`, `context`, `head` and `status` operations remain available for the CommunityHero server. Every result carries `account` and `accountBinding`.

Bridge assistant requests also require the selected provider key; direct legacy preparation calls retain their LikeAvto default. Drafting, triage and public research prompts derive the exact display name from the allowlist, include the account binding in model input, and hash the account-specific instructions into generation metadata. BAW requests therefore cannot reuse LikeAvto prompt identity or wording. The combined v10 drafting/review provenance retains the exact-point evidence rules from the site v8 prompts, including additive comparisons, nearby-model limitations, and avoiding repeated context requests. Supplied account rules and materials remain evidence for the selected workspace; assistant output never grants mutation authority.

Read takes `mode: "open" | "closed"` and an optional opaque `cursor`; each page reads up to 10 items per configured object. Both top-level and `live` include `hasMore`, `cursor`, `scannedCount`, `observedCount` and `coverage`. `observedCount` is the provider-reported count on fetched pages, not a proven account total. `coverage.complete` applies only to the current cursor walk; it never establishes full branch context. Closed history includes items without attachments. Read-only operations construct transports with `executionMode: {mode:"disabled"}` and do not require a reviewed execution config.

Context takes `objectId` and `itemId`. It returns current status, `conversationKey`, `contextEvidenceDigest`, text, parent, actors, `officialReplyIds` and official replies. Branch completeness remains false. Public attachment locators are projected; no raw credential-bearing Provider payload is returned.

Execute/readback take `actions: [{actionId,objectId,itemId,conversationKey,action,reply?,readbackEvidence?,contextEvidenceDigest,expectedStatuses,workTime}]`. The admitted actions are `close`, `delete`, `hide` and `reply_and_close`; `reply` is required only for `reply_and_close`. Reply readback evidence may carry `expectedReplyId`, `baselineReplyIds`, or both. Without identity evidence, a matching reply text remains `unknown`. The backend owns immutable approval, revision checks and attempt persistence. Provider additionally verifies context digest and status. Results preserve `verified`, `failed` and `unknown`; ambiguous attempts must be reconciled and never retried blindly.

Mutation is disabled unless the adapter child starts with `COMMUNITYHERO_EXTERNAL_WRITES=enabled`. `maxInFlight` accepts 1 through 100 and defaults to the admitted action count; `COMMUNITYHERO_MAX_IN_FLIGHT` may set the process default. Execution acquires sorted, account-bound resource locks under `<native.lockDirectory>/communityhero-resource-locks`: every action locks its exact item, and replies additionally lock their conversation. CommunityHero copies using the same validated Provider config therefore share the same locks. Independent items can run in parallel across bridge subprocesses, while the same item and two replies in one conversation fail closed with `ACCOUNT_EXECUTION_BUSY`. Conflict detection matches the same account or the same account config path, so an unrelated account is not treated as a global conflict. The existing conveyor does not acquire these MVP locks, so a sole active operator remains required per account. A stale resource lock fails closed and requires owner investigation; it is never silently reclaimed. Development acceptance has not sent, closed or otherwise mutated a social-network comment.

Child execution uses fixed binaries with `shell: false`. Timeout or signal cancellation kills the Windows descendant tree before releasing adapter ownership. Errors exposed on stdout are codes only. Model isolation and media availability remain separate capabilities documented by their implementations and canary results.
