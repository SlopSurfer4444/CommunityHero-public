# ADR 0002: CommunityHero owns the product; connectors are replaceable

Решение владельца: 22.09.2026. Статус: принято как архитектурное направление.
Это фиксация границы и критериев дальнейшей работы, не заявление о завершённом
рефакторинге. Работающий сервер, база и входящий пакет движка не менялись.

## Решение

CommunityHero строится с расчётом на прямые API социальных сетей. Angry.Space —
временный посредник. Его удаление должно требовать замены подключения и явного
сопоставления внешних объектов, а не переписывания продукта и потери истории.

Сохраняем общий Rust-движок, PostgreSQL, очередь, подготовку ответов, ассистента,
расшифровки, знания и обратную связь операторов. Сайт и standalone CLI используют
те же продуктовые правила и одну систему подтверждений/операций.

| Принадлежит CommunityHero | Принадлежит конкретному коннектору |
|---|---|
| Внутренние ID комментариев, публикаций, обсуждений и рабочих задач | Внешние ID и их подтверждённое сопоставление |
| Статус работы оператора: нужно участие, подготовлено, ожидаем, завершено | Наблюдаемый статус источника, включая статус очереди посредника |
| Черновики, решения, версии контекста, проверка и подтверждение | Протокол публикации, модерации и проверки результата |
| Durable jobs, intent операции, аудит, UNKNOWN и восстановление | Квитанция API, трактовка ошибок, лимиты и Retry-After |
| Семантика полноты/свежести синхронизации и дедупликация | Webhook/polling, непрозрачный курсор, страницы и преобразование событий |
| Знания, feedback, контекст видео и происхождение материалов | Получение доступных данных/медиа и ссылки на оригиналы |

Правила ответа принадлежат аккаунту/бренду и продукту. Ограничения конкретной
площадки учитываются через возможности подключения, а не через название
посредника в общих правилах подготовки.

## Что нельзя смешивать

1. **Завершение рабочей задачи и внешнее действие.** «Закрыть без ответа» —
   полноценное локальное решение CommunityHero. Синхронизация этого решения с
   очередью Angry.Space, если нужна, — отдельный поддерживаемый эффект адаптера.
   Прямому API не требуется придумывать аналог inbox-close. Публикация ответа
   и завершение работы имеют отдельные результаты; частичный успех не теряется.
2. **Внутренняя сущность и внешняя ссылка.** Храним внутреннюю идентичность и
   привязанные к подключению внешние ссылки. Смена транспорта не создаёт новую
   рабочую историю для того же доказанно сопоставленного комментария. Отсутствие
   сопоставления означает неизвестность, а не разрешение угадать ID.
3. **Решение и право исполнения.** Предложение, подтверждение и операция связаны
   с точной версией подключения/адресата. Старые подтверждения не переезжают на
   новый API автоматически; UNKNOWN не повторяется через другой коннектор.
4. **Поддержка возможности и наличие типа в коде.** Publish/hide/delete/restore
   подтверждаются отдельно для конкретного подключения. Отсутствие поддержки
   не маскируется другой операцией. Все API не обязаны иметь одинаковые функции.
5. **Ошибка или неполное чтение и исчезновение объекта.** Неполная страница,
   отказ доступа и временная ошибка не становятся событиями закрытия/удаления.

При совместном чтении через посредника и native API нужен общий учёт одной
канонической сущности. Во время перехода сохраняется один исполнитель для неё;
смена binding не должна обходить блокировку неопределённой отправки. Пока
сопоставление не доказано, перекрывающиеся исполнители не включаются.

## Что уже есть и где остаётся зависимость

По проверке исходников после слияния 22–23.09.2026:

- `mvp/server/src/connectors.rs` содержит binding, непрозрачные внешние ссылки,
  capabilities, отдельные действия, курсор, receipts/readback и интерфейс
  Connector. Это полезная основа, но не доказательство готовых native API.
- `accounts.rs` явно выбирает LikeAvto или BAW для отдельной базы и сохраняет
  уже существующую корректную native-привязку. Создание начального Angry.Space
  binding и legacy `close`/`reply_and_close` ещё требуют дальнейшего отделения
  от продуктового плана действий. Поддержка двух аккаунтов не означает готовность
  прямого API социальной сети.
- `fast_status.rs`, `sync_scan.rs` и merge в `main.rs` местами принимают решения
  по `providerStatus` со значениями `new/inprogress/closed/deleted`. Требуется
  разделить состояние рабочей задачи, наблюдение посредника и состояние самого
  социального объекта; сохранить действующие проверки свежести и версий.
- `mvp/adapters/provider.mjs` преобразует данные и команды Angry.Space; это
  правильное место для его wire-контракта. Специфичные object IDs, составные ключи
  и обязательное закрытие не должны становиться общими требованиями адаптеров.
- `config.mjs` и fallback пути запуска ещё знают локальные репозитории
  Angry.Space. Для другого коннектора их отсутствие не должно мешать запуску.

Историческая записка `project/connector-boundary-2026-09-21.md` описывает более
ранний этап. Её сведения о SQLite/недоступности PostgreSQL не отражают текущий
сервер. Общую целевую модель продолжает задавать
`project/specs/communityhero-canonical-connector-data-model-v1.md`.

## Приём входящего пакета общего движка

При следующей разрешённой интеграции сохраняем универсальные механизмы:
изоляцию аккаунтов, подготовку и исследование, resumable scan с coverage,
точные подтверждения, сериализацию конфликтующих операций, durable receipts,
карантин UNKNOWN и проверку результата. Provider 1.1 рассматривается как
контракт адаптера Angry.Space; он не определяет всю предметную модель продукта.

Сначала сопоставляем эти механизмы с текущими изменениями сайта. Не заменяем
каталог backend или схему базы копией пакета. Не переносим в ядро новые
зависимости от Angry.Space только потому, что они удобны standalone-клиенту.
UI сохраняет preview/edit/approve. Новые функции прямых API и их включение —
отдельные изменения, с проверкой реальных возможностей выбранной площадки.

## Критерии готовности к замене посредника

- Одинаковые сценарии ядра проходят с fake Angry.Space и независимым fake native
  connector. Во втором сценарии нет вызовов или обязательной конфигурации Angry.
- Native-сценарий работает без внешней команды закрытия карточки; локальное
  решение, публикация и возможная частичная ошибка сохраняются корректно.
- После смены подключения сохраняются канонические ID, черновики, материалы,
  feedback и аудит; свежесть контекста и право исполнения проверяются заново.
- Проверены совпадающие внешние ID разных подключений, события из двух путей,
  поздний readback, устаревшее подтверждение и UNKNOWN при отключении посредника.
- Коннекторы проходят общий контракт чтения/полноты, capabilities, исполнения,
  ошибок и readback; отдельно проверяются особенности каждой площадки.
- На копии базы проверяется миграция алиасов и история старых операций.
  Затем — разрешённая read-only проверка native API и отдельный live canary.

Эти критерии ещё не означают, что соответствующие миграции и тесты реализованы.
Отключение Angry.Space не должно удалять исторические доказательства операций.

## Видео — функция CommunityHero

Транскрипция принадлежит CommunityHero и компании. Коннектор даёт источник медиа:
URL либо ссылку на asset, привязку к компании/публикации и происхождение. Он не
владеет ASR, OCR, кешем или итоговым материалом. Прямые API и загрузка файла
должны использовать тот же процесс обработки, без обязательного Angry.Space ID.

Следующий отдельный этап — перенести orchestration загрузки, FFmpeg, native
Whisper CUDA large-v3 и необходимого OCR/очистки в Rust, с сохранёнными заданиями,
таймаутами, восстановлением, сопоставлением дублей внутри компании и версиями
знаний. Whisper и FFmpeg не переписываются; внешний yt-dlp может оставаться
зависимостью. Это не обещание отсутствия Python.

Сейчас `materials.py` всё ещё импортирует `commentops_fast.media`, а конфигурация
использует внешний runtime. До успешной реальной расшифровки, чтения результата
из БД и проверки восстановления при сбое сохраняются библиотека, её транзитивные
зависимости и assets. Закрытие старого CLI не разрешает удалять эту библиотеку.
Новый UI и внешняя публикация в этот этап не входят.
